## What was proven

1. **The `CONTENT_AUTHZ` authorization extension imports with no allowlist
   gating.** This is HAC-325 question 1 and canon open item **O-9**. The
   `gcloud network-services agent-gateways` and `gcloud service-extensions
   authz-extensions` command groups are present in **GA** gcloud 580.0.0, no
   preview component or enrollment was required, and the import succeeded.
   Evidence: `evidence/authz-extension.json`.
2. **The Agent Gateway provisions with the ADR's network topology** — PSC
   `networkConfig.egress.networkAttachment` into the experiment VPC and
   `networkConfig.dnsPeeringConfig` for the internal FQDN. Both ingress
   (`CLIENT_TO_AGENT`) and egress (`AGENT_TO_ANYWHERE`) gateways were created.
   Evidence: `evidence/agent-gateway-egress.json`.
3. **A `CONTENT_AUTHZ` policy binds the extension to the gateway**, with
   `action: CUSTOM` and `customProvider.authzExtension`.
   Evidence: `evidence/authz-policy-egress.json`.
4. **The Cloud Run `ext_proc` extension deploys and runs** behind a Serverless
   NEG, a regional `INTERNAL_MANAGED` backend service, an internal forwarding
   rule, and a private Cloud DNS zone resolving `ext.s0.interlock.internal`.
5. **The egress gateway does intercept agent egress.** Proven indirectly but
   unambiguously: binding `agentToAnywhereConfig` caused the agent's *own*
   outbound TLS to be terminated by the gateway (see the blocker below). The
   data path exists.

## The blocker, exactly

Binding an `AGENT_TO_ANYWHERE` gateway routes **all** of the agent's outbound
traffic through the gateway, which performs TLS decryption and inspection. Agent
Runtime's own managed **session service** is on that path:

```
google.auth.exceptions.TransportError: Failed to send request to
  https://us-central1-aiplatform.mtls.googleapis.com/v1beta1/projects/
  interlock-s0-gate/locations/us-central1/reasoningEngines/6822295377757077504/sessions

aiohttp.client_exceptions.ClientConnectorCertificateError:
  [SSL: CERTIFICATE_VERIFY_FAILED] self-signed certificate in certificate chain

grpc: Tls handshake failed (TSI_PROTOCOL_FAILURE): CERTIFICATE_VERIFY_FAILED
RuntimeError: Failed to create session.
```

Every published invocation method on the reasoning engine — `stream_query`,
`async_stream_query`, `streaming_agent_run_with_events` — creates a session
first. Session creation fails, so the agent body never executes, so it never
emits the MCP call the `CONTENT_AUTHZ` extension would inspect.

The documentation states that source-based (non-BYOC) deployments *automatically
inject the gateway CA certificate during image creation*. The agent was
redeployed from source **after** the egress binding existed, so the injection
should have applied. It did not resolve the failure for either `aiohttp` or
gRPC. Evidence: `evidence/blocker-tls-interception.json`.

This is the certificate prerequisite HAC-325 asked about, and it is more
consequential than expected: it is not a property of the extension path but of
the whole egress path.

## Corrections the running system forced

Recorded because each one is a real prerequisite that the documentation and
schema did not convey, and each cost a provisioning cycle.

1. **Cloud Build on a fresh project.** The Compute Engine default service
   account needs `roles/cloudbuild.builds.builder`. Without it `builds submit`
   fails with a `storage.objects.get` 403 on its own staging bucket, which reads
   like a bucket fault rather than a missing role.
2. **`AuthzExtension.timeout` is a protobuf `Duration`.** The schema documents
   the bound as 10–10000 **milliseconds**, but `1000ms` is rejected with
   `Invalid duration format, failed to parse seconds`. It must be written `1s`.
   The usable envelope is therefore `0.010s`–`10s`.
3. **An Agent Gateway target carries no load balancing scheme.** The gcloud
   schema says `service` must be a fully-qualified backend service and that
   `authority` is then required — but that form forces `INTERNAL_MANAGED` and is
   rejected for gateway targets with *"authz extension load balancing scheme
   INTERNAL_MANAGED must match the authz policy load balancing scheme
   LOAD_BALANCING_SCHEME_UNSPECIFIED"*. For gateway targets the **FQDN form is
   mandatory** and `loadBalancingScheme` must be omitted. The published
   `service: mycustomauthz.internal.net` example is correct; the schema misleads.
4. **`protocols` accepts only `MCP`.** An Agent Gateway governs MCP traffic. It
   does not govern Vertex's own `streamQuery` API, so an ingress gateway placed
   in front of a reasoning engine never sees that call.
5. **An Agent Gateway has no callable endpoint of its own.** No `endpoint` field
   exists on the resource in `v1`, `v1beta1` or `v1alpha1`, and none is
   documented. Traffic reaches a gateway only because a workload is *bound* to
   it — `spec.deploymentSpec.agentGatewayConfig` on a reasoning engine. You
   cannot curl a gateway.
6. **`agentGatewayConfig` requires `identityType: AGENT_IDENTITY`**, rejected
   otherwise with `FAILED_PRECONDITION`.
7. **Retargeting an existing `AuthzPolicy` to a different gateway fails** with
   `code 13, an internal error has occurred`. The policy must be deleted and
   recreated.
8. **Re-adding an already-attached serverless NEG** reports a bogus
   `Invalid Serverless Network Endpoint Group scope` rather than a duplicate
   error. The provisioner now checks membership instead.
9. **Org policy `constraints/iam.allowedPolicyMemberDomains`** (restricted to
   customer `C03dzmv5u`) forbids `allUsers`, so the documented requirement that
   a Cloud Run callout backend *"allow unauthenticated access"* cannot be met
   directly. Worked around **without** weakening the org policy by granting
   `roles/run.invoker` to the specific principals:
   `service-708527487974@gcp-sa-dep.iam.gserviceaccount.com` for the extension,
   and the agent's own identity for the target.

## Scope deviation, and why it did not rescue the gate

S0 was first attempted with an **ingress** (`CLIENT_TO_AGENT`) gateway rather
than the ADR's egress design, on the reasoning that the egress YAML requires an
Agent Registry and agent workloads that HAC-325 excludes. Findings 4 and 5 above
falsified that reasoning: the extension mechanism is reachable in neither
direction without a bound Agent Runtime workload, and MCP is the only governed
protocol. The experiment was moved to the ADR's egress design, which is where
the TLS blocker was found. The ADR's original egress choice was correct.

## Static analysis on the experiment code

The required `SonarCloud Code Analysis` gate failed this PR on
`new_security_rating` = C against a threshold of A. Five vulnerabilities, all in
code added here. Four were real and were fixed rather than excluded, per the
merge-gate matrix rule that SonarQube Cloud owns new-code security and a gate is
not weakened to recover green:

| Rule | Finding | Fix |
| -- | -- | -- |
| `docker:S6471` ×2 | both images ran as root | drop to uid 10001 |
| `docker:S8541` | `pip` could execute a dependency's `setup.py` | `--only-binary :all:` |
| `docker:S8544` | versions pinned, resolved artifacts not | hash-locked requirements, `--require-hashes` |

Hashes were verified by resolving them with `pip download --require-hashes
--only-binary :all:` for linux/amd64 cp312, the platform Cloud Build targets.

The fifth, `python:S5332` on `target/app.py`, is dispositioned **False Positive**
— not *Accepted*. The distinction matters: *Accepted* records a valid finding
that is being deferred, which would misstate this. The Cloud Run container
runtime contract states that *"the container shouldn't implement any transport
layer security directly"* and that *"TLS is terminated by Cloud Run for HTTPS and
gRPC, and then requests are proxied as HTTP/1 or gRPC to the container without
TLS"*. Serving application-level TLS would contradict the platform contract, so
this is the analyzer being wrong about the context rather than a risk being
accepted.

Worth recording for META-337: four genuine security defects in a disposable,
already-deleted experiment is evidence the gate does work rather than adding
ceremony. That is also why `experiments/**` was **not** excluded from analysis
and why `target/` was **not** deleted to clear the finding — a failed
architecture still needs its reproducible implementation as evidence.

## Disposition

Per HAC-325's fail/pivot clause and the ADR fail action, the preferred
Gateway-extension enforcement point is **not proven** and the bounded MCP/API
proxy fallback is the indicated path. The architecture must **not** be frozen on
this evidence: O-2 stays open, and S2 (HAC-326) cannot proceed against an
unproven insertion point.

What survives for reuse regardless of the pivot: the `ext_proc` extension
implementation, the provisioning and teardown scripts, and every prerequisite in
this receipt.
